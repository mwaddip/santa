# SANTA — AuthDS tier (`santa-authds/v1`, AVL prover + verifier)

> Status: **LIVE** (design approved 2026-08-02, built and mounted 2026-08-03). Durable
> contract: [`docs/contract/runner-contract-authds.md`](../contract/runner-contract-authds.md)
> — this document remains the design record; see "Live board" below for real numbers.
> Tier name: `authds`. Kinds v1: `avl_prove`, `avl_verify`.
> Vectors: `vectors/authds/any/vendored/` — 60 entries (10 prove, 50 verify).

## What & why

A sixth tier grading the **authenticated-data-structure** surface directly: the
AVL+ batch **prover** (produce canonical proof bytes) and the batch **verifier**
(consume them), below the ErgoScript layer that currently reaches them.

The trigger is that **ergots has built an AVL prover** — `packages/avltree`, a
pure-TS `BatchAVLProver` ported from the `mwaddip/ergo_avltree_rust` fork. Until
now every SANTA AVL vector graded verification only: the eval tier's ~30
`AvlTree.*` files hand a proof in as an *input* and grade what ErgoScript makes
of it; the block tier hands `adProofs.proofBytes` in and grades `post_digest`.
Nothing asks an implementation to *emit* a proof.

That matters as soon as a second prover exists. Proof bytes are consensus data —
`blake2b256(proofBytes) == header.adProofsRoot` is a validity rule, and
contract-supplied proofs are verified on-chain. dApp developers will now generate
AVL proofs in TypeScript and hand them to mainnet contracts; a proof the JVM
verifier will not take is stuck funds. The failure mode is live already:
`ADPROOF-FINDING.md` (block 28474) is a valid-but-non-canonical Rust proof, and
it is why that seed is held rather than vectored.

**This is not SANTA's first generative dimension.** The chain tier already grades
produced values — `retargeting` grades a computed `nbits`, `voting` grades a
computed parameter table plus `activated_update`. `avl_prove` fits an existing
pattern rather than establishing a new one.

**Naming.** SANTA tiers are named for subject matter, not direction: `wire`
covers serialization both ways, `chain` already mixes validation
(`fork_vote_gate`, `header_votes`) with production (`retargeting`, `voting`). A
tier named `proof` would be the first named for a role, and would be wrong in the
other direction since verification is proof-shaped too. `authds` is the reference
implementation's own name for exactly this family — the scrypto 3.0.0 jar ships
`scorex/crypto/authds/{avltree, merkle, legacy}` — so it names the subject, keeps
both arms under one roof, and leaves `merkle_*` room without a rename.

## Approach: vendor the inputs, re-bless every expectation

ergots ships 60 fixtures in two families:

| Family | Path | Count | Shape |
|---|---|---|---|
| prover | `packages/avltree/test/fixtures/prover/` | 10 | `{config, operations[], genProofAfter[], expectedProofs[], expectedDigests[]}` |
| verifier | `packages/avltree/test/fixtures/avltree/` | 50 | `{config, startingDigestHex, operations[], proofHex, expectedNewDigestHex, expectedResultsHex[]}` |

The prover fixtures are **Rust-blessed** — `prover-fixtures.test.ts` says so in
its header ("generated by `~/projects/ergo_avltree_rust/tests/prover_fixtures.rs`",
still untracked in the fork). Importing those expectations as-is would make the
vectors structurally incapable of catching a Rust-vs-JVM prover divergence: they
would green ergots and the Rust conformers together against a non-canonical
oracle. That is the exact failure this suite exists to prevent.

So the split is: **inputs vendored, expectations re-derived.** The op sequences,
configs, and `genProofAfter` trigger points are the hard-won part and carry over
verbatim. Every expected byte is re-derived through `jvm-blesser`. The 60
re-blesses are the tier's first finding-generator — any fixture that does not
reproduce is a Rust-vs-JVM divergence found before a single runner is asked
anything.

Re-blessing also **enriches** the corpus. The 50 verifier fixtures collapse three
distinct failure modes into one `expectedNewDigestHex: null`:

- `adverse-truncated-proof` / `adverse-malicious-extra-nodes` — the proof itself
  is rejected; the verifier never builds a tree.
- `adverse-mismatched-config-keylength` — construction parameters disagree with
  the proof.
- `remove-3leaves-absent-fail`, `update-3leaves-absent-fail`,
  `update-long-by-negative-result-fail` — the proof is **fine**; a single
  operation legitimately fails.

The JVM distinguishes all three (verified against the jar):
`BatchAVLVerifier(startingDigest, proof, keyLength, valueLengthOpt,
maxNumOperations, maxDeletes, hf)`, then
`performOneOperation(op): Try[Option[ADValue]]` and `digest(): Option[ADDigest]`.
A single coarse `null` would false-green an implementation that rejects the proof
outright where the JVM accepts the proof and fails only the operation — the
hazard recorded in the reject-arm rule. `santa-authds/v1` keeps the levels
separate.

## Format — `santa-authds/v1`

Mirrors the chain tier's discriminator exactly. Entry:
`{name, source, kind, settings, payload, expected}` plus an `allOf` of
`if kind == X then {settings, payload, expected}` shapes.

**`avl_prove`**

```
settings : { key_length: int, value_length: int|null }
payload  : { operations: [Op], gen_proof_after: [int] }
expected : { proofs: [hex], digests: [hex] }
```

No `initial_entries`. Seeding a tree is just operations with a `gen_proof_after`
at the boundary, which subsumes the split `AvlProofGenerator` uses today and
makes the multi-cycle case first-class instead of bolted on. `gen_proof_after`
holds ascending operation indices; `proofs` and `digests` are parallel arrays of
the same length.

**`avl_verify`**

```
settings : { key_length: int, value_length: int|null,
             max_num_operations: int|null, max_deletes: int|null }
payload  : { starting_digest_hex: hex, proof_hex: hex, operations: [Op] }
expected : { proof_accepted: bool,
             results: [ {ok: bool, value: hex|null} ],
             new_digest_hex: hex|null }
```

`proof_accepted` has a single observable definition, so that two blessers cannot
disagree: **`verifier.digest.isDefined` evaluated immediately after construction,
before any operation is performed.** scrypto's constructor does not throw — it
leaves the tree unbuilt — so `digest()` returning `None` at that point is exactly
"the proof was not accepted at this starting digest under these settings".

When `proof_accepted` is false the blesser **does not attempt the operations**:
`results` is `[]` and `new_digest_hex` is null, by convention. (Running them
would produce a uniform row of `{ok: false}` that carries no information and
invites a conformer to match the shape without reproducing the rejection.)
Otherwise `results` has one entry per operation
— `{ok: true, value: <hex>}` for `Success(Some)`, `{ok: true, value: null}` for
`Success(None)`, `{ok: false, value: null}` for `Failure` — and `new_digest_hex`
is the final digest, or null if any operation broke the verifier.

**Operation encoding** (shared): `{tag, key_hex, value_hex?, delta?}` with tags
`Insert`, `Update`, `Remove`, `Lookup`, `InsertOrUpdate`, `RemoveIfExists`,
`UpdateLongBy`, `UnknownModification`. `delta` is a decimal **string** for
`UpdateLongBy` (Long range; the eval tier's Long-as-string rule applies
pre-emptively — a JSON number loses precision past 2^53. No delta in the current
corpus needs it, the largest `|delta|` anywhere is `100`; a future fixture could
still carry one beyond the safe-integer bound). All hex lower-case.

## Result shape (runner contract)

```
avl_prove  actuals : { proofs: [hex], digests: [hex], error: string|null }
avl_verify actuals : { proof_accepted: bool, results: [...],
                       new_digest_hex: hex|null, error: string|null }
```

Standard outcome vocabulary — `errored`, `not-implemented`, `panicked`. A
conformer with no prover declares `not-implemented` on `avl_prove`; that is a
growth-ledger cell, not a gap.

## Grading — `grade_authds`

**`avl_prove` — `proof` and `digest` are INDEPENDENT dimensions, graded per ENTRY.**
Each dimension is one verdict per entry over the *whole* `proofs`/`digests` array,
positionally — not per individual `gen_proof_after` cycle: an entry with 3 proof
cycles still contributes exactly one `proof` verdict and one `digest` verdict, so
`authds_proof_total` counts entries (10), not cycles (18). Deliberately *not*
chained, breaking with the block tier's `valid → post_digest → cost` suppression.
Rationale: digest-correct-but-proof-bytes-different is precisely the
ADPROOF-FINDING class, the single most important signal this arm exists to
surface. Chaining would hide it behind a green digest.

**`avl_verify` — chained `proof_accepted → results → new_digest`.** An upstream
failure suppresses the downstream dimensions, matching block. Note the order:
the digest is downstream of the operations, not parallel to them.

**Reject arm.** The adverse fixtures are the over-accept probes. Per the
reject-arm rule, confirm at conform that each expected diverger is actually RED
and for the intended reason — a fixture that errors incidentally (malformed input
rather than a real leniency) false-greens under coarse grading and must be
rebuilt rather than counted.

## Blesser (JVM) — `jvm-blesser/`

- **`AvlProofGenerator`** grows `gen_proof_after` multi-cycle support, replacing
  the current `initial_entries` + implicit-commit split. `POST /avl-proof` gains
  the same field but **keeps `initial_entries` working** — the open 28474 /
  genesis investigation drives that endpoint and must not be broken.
- **`AvlVerifierBlesser`** (new) — construct `BatchAVLVerifier`, run
  `performOneOperation` per op, capture the `Try[Option[ADValue]]` per op and the
  final `digest(): Option`.
- Fail-loud re-derive tests `VendoredAuthdsAvlProve{,Test}` /
  `VendoredAuthdsAvlVerify{,Test}`, per the established pattern.
- `blessed_by: "jvm:scrypto-3.0.0"` — scrypto is the actual authority for this
  tier, not sigma-state.

## Vectors / taxonomy

`vectors/authds/any/vendored/` — **`any`** because AVL proofs are not
ErgoTree-versioned, matching how chain files `Retargeting` and `HeaderVotes`.
Provenance **`vendored`**, following the wire tier's ergots+Fleet precedent:
`source: "ergots:packages/avltree/test/fixtures/<set>/<name>.json"`.

## Predicted findings

- **vixen adverse verify → `panicked`.** arkadianet runs crates.io
  `ergo_avltree_rust 0.1.1`, the version blitzen-eni's own manifest describes as
  "`.unwrap()`-heavy verifier panics on malformed proofs / out-of-range params".
  The four adverse fixtures aim straight at it.
- **eni + donner verify graded pre-hardening.** Both lock `2fc88d83`, before
  `3326484` (return `Err` instead of panicking) and `282f7da` (deserialization
  input validation). These are pin artefacts, not implementation findings —
  routed via `prompts/ergo-node-rust-avltree-branch-tracking.md`.
- **The 10 prover re-blesses.** Any mismatch is a Rust-vs-JVM prover divergence.
  The prover core was verified byte-identical to the JVM across four cases
  (`prompts/ergo-avltree-canonical-proof-resolved.md`), so the expectation is
  convergence — and convergence across 10 richer multi-cycle sequences is itself
  the result, given block 28474 remains unexplained upstream of the prover.
  **Outcome: 10/10 converged.**

## Confirmed findings

- **`UnknownModification` is a keyless singleton in scrypto, a keyed lookup
  everywhere else — but NOT a consensus divergence** —
  [`docs/findings/authds-unknownmodification-jvm-vs-rust.md`](../findings/authds-unknownmodification-jvm-vs-rust.md).
  Originally surfaced by the 50 verifier re-blesses (46/50 agreed with the JVM; all
  four that did not contained the tag): scrypto rejects it, the fixed zero-length key
  sorting below −inf, and poisons the verifier, where `ergo_avltree_rust` / ergots
  honour the caller's key and treat it as a non-modifying lookup.
  **Retired 2026-08-04.** The operation is unreachable — `UnknownModification`,
  `UpdateLongBy` and `RemoveIfExists` all have **zero** fully-qualified references in
  sigma-state 6.0.3 or ergo-core, so nothing an ErgoScript contract or the node can do
  constructs them. A disagreement about behaviour no consensus path can observe is not
  a conformance divergence. The 13 fixtures exercising them moved to
  [`unreachable/`](../../unreachable/README.md) — preserved rather than deleted, since
  dead code can be revived — and the corpus is now **37 verifier entries, 37/37
  agreeing with the JVM**.

## Honest limitations

- **Thin prover diversity.** Three cells on the prove arm, but rudolph *is* the
  oracle and vixen runs the same Rust crate family as the fork. **dasher is the
  only genuinely independent prover** under test. That is the point — it is the
  new one — but the board will look wider than the evidence is.
- **Sigma-protocol proving does not fit this tier.** Spending proofs are the
  thing SANTA is named for, but Fiat-Shamir is non-deterministic and the runner
  contract forbids an oracle dependency at conformance time, so there is no
  committable expected without an injected-randomness seam in every
  implementation — a four-codebase coordination ask, not a SANTA decision. Its
  deterministic half, reduction to a sigma tree, is already graded in eval
  (`{"kind": "SigmaProp", "raw_hex": ...}`).
- **The verify arm reaches below consensus.** On-chain `AvlTree` values carry
  their config from the tree constant, so the eval tier only ever exercises the
  configs its own vectors pin. The vendored config-variance fixtures
  (`keyLength` 1 and 8, fixed `valueLength`, `maxNumOperations` bounds) reach
  library surface that consensus touches only through ErgoScript. That is a
  deliberate widening, accepted when this tier was scoped.
- **Two of the 50 verify entries are the same test.** `config-variance-max-ops-exact`
  and `lookup-3leaves-present` are byte-identical in `settings`, `payload`, and
  `expected` — 50 named entries, 49 distinct inputs. The duplicate's name promises
  a `max_num_operations`-at-the-exact-bound cell it does not actually add (the
  plain lookup already carries `max_num_operations: 1` with one operation).
  Inherited from ergots' upstream fixture set, not introduced by re-blessing; the
  committed vector is not being deduplicated or regenerated over it — recorded
  here as a known coverage gap.

## Gates / testing (TDD)

- Blesser tests fail loud — a re-derive that cannot reproduce a committed
  expectation is a build failure, not a warning.
- `santa-check` unit + oracle meta-vectors green before any runner arm lands.
- `validate` passes on all 60 before commit.
- rudolph green on both kinds is the precondition for reading any other cell.

## Out of scope / Deferred

- **`merkle_*` kinds** — `transactionsRoot` construction and `BatchMerkleProof`
  (Extension section, light-client `proofFor`). Same family, same tier, later;
  the `kind` discriminator is here so they land without schema churn.
- **NiPoPoW interlinks** — needs chain context deeper than any current format.
- **Sigma prover** — see limitations above.
- **`PersistentBatchAVLProver` / storage-backed rollback** — the fork's
  `restore_root`, `flush`, and resolver surface are enr/arkadianet concerns and
  are not consensus-visible.
- **Block 28474 as a vector** — still held. This tier makes the prover
  gradeable, but 28474's divergence was traced *upstream* of the prover, to
  operation construction or tree-state materialization
  (`prompts/ergo-avltree-canonical-proof-serialization.md`). Vectoring it needs
  the block tier, not this one.
